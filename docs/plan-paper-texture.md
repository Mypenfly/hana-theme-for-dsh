## 0. 参考的实现,完整读一遍

参考自己的 `styles.css` 把这件事写成了三条注释:

```css
/* ========================================
   纸质纹理系统
   开关：body.paper-texture 显式开启全部纹理
   三层：surface → card → surface 亮度补偿
   新增 card 元素只需往 Card 层追加选择器
   ======================================== */
```

**三层,逐条:**

**① Surface 层** —— 纹理画在**铺底元素自己的 `background-image`** 上:

```css
body.paper-texture,
body.paper-texture .titlebar,
body.paper-texture .sidebar {
    background-image: url(./assets/textures/rice-paper.png);
    background-repeat: repeat; background-size: 160px; background-attachment: fixed;
}
```

**② Card 层** —— **同一张纹理**,画在每一个 `bg-card` 元素自己的 `background-image` 上,
外加一个混合模式令牌(`styles.css` 里列了 14 个选择器,`Settings.module.css` 里另有一批):

```css
body.paper-texture .universal-card, … .ob-input, … .hana-toast, … {
    background-image: url(./assets/textures/rice-paper.png);
    background-repeat: repeat; background-size: 160px; background-attachment: fixed;
    background-blend-mode: var(--paper-texture-card-blend-mode);   /* 默认 lighten */
}
```

**③ 亮度补偿层** —— 一块固定的暖白,压在**画布之上、面板之下**:

```css
html:not([data-theme="midnight"]):not([data-theme="midnight-contrast"]) body.paper-texture::before {
    content: ''; position: fixed; inset: 0; z-index: -1; pointer-events: none;
    background: rgba(255, 253, 247, 0.35);
}
```

**暗色否决** —— 不在 CSS 里,在**注册表**里(`shared/theme-registry-data.json`):

```json
"paperTextureBlockedThemeIds": ["midnight", "midnight-contrast"]
```

```ts
export function isPaperTextureEffectivelyEnabled(enabled, theme) {
  return enabled && !isPaperTextureBlockedTheme(theme);
}
```

即:**暗色主题下 `body.paper-texture` 这个 class 根本不会被加上**。设置页把开关
**禁用**并换一句提示(`locales/zh.json`):**「黑夜模式不支持纸质纹理,切回浅色主题后
会按原设置恢复」** —— 用户的偏好**不被改写**。

参考自己的契约测试 `tests/paper-texture-contract.test.ts` 守着这些:
第一条用例的名字就是 **"turns off card texture brightness compensation in both dark themes"**。

### 0.1 三层各自在做什么(实测出来的,不是读注释)

把 `rice-paper.png` 量一下(500×500 RGBA):

| | 值 |
|---|---|
| 平均色 | **(192.2, 182.2, 166.6)** —— 一块**暖灰**,比任何纸底都深 |
| 色通道标准差 | 2.9 / 1.9 / 3.4 —— **几乎是常数** |
| 平均 alpha | **62.1/255 = 0.244** |
| alpha 标准差 | 10.6/255 |

**所以这张纹理是"一块恒定的暖灰 + 变化的覆盖率",不是"有颜色的噪点"。**
它以 `normal` 合成,于是**纸底被压深**:纸本 `#F5EFE4`(245,239,228) →
(232.0, 225.0, 212.6),**掉了 13–15/255,约 5%**。③ 那块暖白把它抬回来约 60%
(→ (240.1, 234.8, 224.7))。**③ 的存在理由就是 ① 的变暗。**

**② 则是另一回事,而且比看上去弱。** `background-blend-mode: lighten` 的语义是
`max(元素底色, 纹理色)`,而纹理色是 192/182/166 —— **比参考七个可用主题里的每一张
卡都深**(最深的 `delve` 卡是 `#F7F7F8`)。所以 `lighten` 的结果**就是卡色本身**:
**在暗色主题被否决之后,② 在每一个真正跑纹理的主题里都是空操作。**
它真正的作用是**一条兜底保证:纹理永远不许把卡压暗**。这也是为什么暗色主题要把这个
令牌从 `lighten` 改成 `normal` —— 暗色的卡比纹理浅不了多少,`lighten` 会把整张卡
换成那块暖灰。契约测试正是守着这一条。

## 1. 我们现在的做法,和它差在哪

`lib/client.js` 现在是**一层**:一个 `z-index: 2147483647` 的整屏 `::after`,
`mix-blend-mode: soft-light`,`opacity: var(--hana-grain-opacity, 0.32)`。

`soft-light` 在**正好中灰**处返回背景色不变,而 `feTurbulence` 的 `fractalNoise`
关于 0.5 对称 —— 所以这一层是**严格明度中性**的。这就是 §0.3 E17–E19 记下的那处偏离:

> 亮度补偿 —— 由 `soft-light` 的数学性质承担,**不额外加补偿层**

而 `test/contrast.test.js` 的 **#24/#25** 把这句承诺变成了算术:5 个背景值上
`softLight(cb, 0.5) === cb`(误差 < 1e-12),四套配色 × 两档强度下合成对比度移动 < 0.3。

### 1.1 颗粒本身的实测对比

在**显示尺寸**下量(主题的 `background-size` 是 160px,所以 500px 的源被缩到 160px,
160px 的 SVG 是 1:1 —— 在别的尺度上量的是没人看得见的东西):

| | 平均色 | 色 sd | 平均 alpha | alpha sd | 相邻像素 alpha 差 |
|---|---|---|---|---|---|
| `rice-paper.png` @160 | (192, 182, 167) | 2.9 | **62** | 10.6 | 10.4 |
| 我们的 SVG @160 | (187, 187, 187) | 15.4 | 127.5 | 30.4 | 34.0 |

两处差别,一处不是差别:

- **覆盖面**:我们的 alpha 平均 127.5,但整层还要乘 `opacity: 0.32` → 有效 40.8,
  参考是 62。**默认档比参考淡**,而我们的上限(0.60 → 76.5)比参考重。
  这是**强度旋钮的位置问题,不是机制问题** —— 记在这里,不动默认值(见 §4)。
- **色相**:参考是恒定暖灰,我们是中性灰。**不动,理由在 §3.2。**
- **空间频率**:**不是差别。** 归一化之后(相邻差 ÷ sd)参考是 0.98、我们是 1.12 ——
  两者在显示尺寸下都**接近逐像素不相关**。500px 的纤维被缩到 160px 之后,
  结构已经被抹平成噪声了。**"我们的颗粒太细" 是错的。**

## 2. 暗色否决 —— 实施

**这是这一项里唯一一个既能做、又确实缺着的部分。** 我们四套配色里,
**青夜与斑斓现在都在跑纸纹**,而参考在这两套上是明确不跑的。

`lib/client.js` 新增一个判据,并把 `data-hana-texture` 与它相与:

```js
/* 参考用一张字面 id 表,因为它自己的注册表就是一张字面表;
   我们的 PALETTE_DEFS 已经带了 scheme,所以按 SCHEME 判 ——
   第五套配色是"由构造被否决",而不是"要有人记得往表里追加"。 */
function textureAllowed(paletteId) {
  var def = paletteById(paletteId);
  return def === null ? true : def.scheme !== "dark";
}
```

设置面板同步三件事(照参考的行为,不是照它的实现):
1. 开关**显示为关**;
2. 开关**禁用**(`disabled`),不是"能用但没用";
3. 提示语换成参考那句:**「黑夜模式不支持纸质纹理,切回浅色主题后会按原设置恢复。」**
4. **存下来的偏好一个字节都不改** —— 切回亮色配色,纸纹按原设置回来。

### 2.1 外加一道 CSS 兜底,理由是**我们自己的**而不是参考的

参考的 CSS 也有兜底(`html:not([data-theme=midnight]):not([data-theme=midnight-contrast])`),
因为它的 class 由好几条路径加(启动、设置同步、换主题)。我们只有一条路径,但有一条
**参考没有的风险**:`data-hana-theme` 与 `data-hana-texture` 是**同一次 reconcile 里
先后写上去的两个属性**,中间只要有一次异常或一次错序,暗色配色就会带着纸纹渲染一帧。

所以纸纹规则**按配色键**(判据 8 从这一轮起就接受按配色键的选择器,并且会把值核对到
出货的配色 id 上),让**画面只依赖配色属性** —— 两个属性再也不可能在屏幕上不一致。

## 3. 三层:逐个判定,逐个给证据

| 参考层 | 参考的落点 | DSH 里这个落点是什么 | 判定 |
|---|---|---|---|
| ① Surface | 铺底元素自己的 `background-image`(**在内容之下**) | "地面"是 `._1qAH1q_frame` | ❌ 够不到 |
| ② Card | 每张卡的 `background-image` + `background-blend-mode` | 卡类全是构建哈希 | ❌ 够不到,**而且实测是空操作** |
| ③ 补偿 | `body::before` + `z-index:-1`(画布之上、面板之下) | **同一个槽位可达**,但被 AppFrame 盖住 | ❌ 够不到,**而且不需要** |

### 3.1 ① 的落点为什么够不到(这一条是这一项的技术核心)

DSH **没有把地面画在 `body` 上**。`body` 的 `background: var(--dsw-alias-bg-base)`
会被传播到画布,而**应用自己在 frame 上又画了一遍**:

```css
/* dsh-client-ui-layout · AppFrame.module.css */
._1qAH1q_frame { background: var(--dsw-alias-bg-base); height: 100%; … }
```

`._1qAH1q_frame` 是**普通流内的块级后代**,而一个负 z-index 的定位元素画在
"层叠上下文自己的背景之上、在流内块级后代的背景之下" —— 也就是说,
**任何 `z-index:-1` 的纹理层都会被 AppFrame 整块盖住**。同样的还有
`.uPhUma_root`(conversation)、`.eAf-nq_root`(chat)、`.isi5dq_panel`(sidebar-right),
各自把自己的那一列重画一遍。

**参考的三层全部落在"元素自己的背景"或"负 z-index"这两个槽里,而 DSH 把这两个槽
都关上了** —— 它把地面画在 frame 层,不是 `body` 层。

我们能用的槽只剩一个:**内容之上的整屏层**。参考**根本不用**这个槽。
所以 §7 那一行原文说的"整屏单层替代三层逐面板"不是省事,是**没有第二个槽**。

### 3.2 ② 为什么不做:它实测是空操作

`lighten` = `max(元素底色, 纹理色)`。纹理色 (192,182,166);参考七个可用主题的卡色
分别是 `#FBF7EE` `#FFFBF3` `#FDFBFA` `#F8F9FB` `#F9FBF7` `#FAF9F5` `#F8F8FA`
—— **每一个都比纹理浅**,于是 `max` 返回卡色本身,**纹理在卡上一像素都不显示**。

换句话说:**② 的全部作用是一条保证(纹理不许把卡压暗),而这条保证我们的实现免费就有**
—— `soft-light` 在中灰处严格中性,#24 逐点证明。**层的目的达到了,层的机制不需要。**

### 3.3 ③ 为什么不做:它补偿的是一次**不会发生的**变暗

这是三条里最要紧的一条,而且它是**算出来的**。

**③ 的因果链,量清楚:** 参考的纹理以 `normal` 合成,恒定暖灰 (192.2,182.2,166.6)
覆盖 24.4%,把纸本的地面从 (245,239,228) 压到 **(232.1, 225.2, 213.0)** ——
掉 12.9/13.8/15.0。然后那块 `rgba(255,253,247,0.35)` 抬回 8.0/9.7/11.9,
即**找回 62%/70%/79%**。**③ 是 ① 的函数,没有 ① 的变暗就没有 ③ 的理由。**

**我们的 ① 不变暗**:`soft-light` 在正好中灰处返回背景色不变,噪声关于 0.5 对称,
#24 在 5 个背景值上逐点证明(误差 < 1e-12),#25 在四套配色 × 两档强度上算出
合成对比度移动 < 0.3。**所以把 ③ 搬过来,它不是补偿,而是一次 35% 暖白的
整体提亮** —— 那是改配色,不是补纸纹。

**它要付的代价也量出来了**(`tools/derive-grain.mjs` 每次 `--check` 都重算):

| 配色 | 卡对底 | 铺上参考那块补偿之后 |
|---|---|---|
| 纸本 | 1.0818 | **1.0374** |
| 珊瑚 | **1.0396** | **1.0202** |

珊瑚本来就贴着 `SEPARATION_FLOOR = 1.02` 走,这一层会把它压到**离地板 0.0002**。
一层的代价是另一套配色全部余量,而换来的是一次没有原因的提亮。

**注意这一条不是"我们差一点就违规了"** —— 1.0202 仍然过。它说的是:
把一个**不可达**的层硬搬进来,会让一个**已经贴地**的断言失去全部余量,
而这个层对我们**一个像素的好处都没有**。

`tools/derive-grain.mjs` 把整条链都算一遍:参考文献的覆盖率与颜色、我们地面的
实际合成、参考那层补偿会抬多少、以及四套配色还剩多少分离度。**如果哪天我们的
颗粒不再是中性的,这个工具会立刻算出"需要多少补偿"** —— 那时 ③ 就从"不该做"
变成"必须做",而门会先说出来。

## 4. 有意没动的两处

**默认强度仍是 32%。** §1.1 量出参考的有效覆盖率是 62 而我们的默认档是 40.8 ——
看着像"该调高到 49%"。**没那么做**:两者的合成模式不同(`normal` 压深 vs
`soft-light` 中性),alpha 不能直接比;而且换默认值是一次**只有用户能判断**的
观感改动,滑块就在设置页上。记下来,把判断留给看得见的人。

**颗粒不染暖色。** 参考的纹理是一块暖灰,会在页面上加一丝暖调;我们是中性灰,
不加。**理由是中性的** —— 不是"我们更对",而是**整套对比度体系建立在这个中性上**:
#24 要求噪声关于 0.5 对称,#25 用对称性算合成后的对比度,四套配色的每一个断言
都以此为地基。染暖色就要先把这套模型改成"每通道各自的中心",而那笔账要由
**配色**来还 —— 而配色的暖,本来就该由配色决定,不该由颗粒偷偷加。

## 6. 实施记录:门自己抓到的两件事

这一项**没有**发生前几项那种"方案被推翻"的戏剧性 —— 它是一句话被拆成了一个能做的
和两个算得出来不该做的。但**变异测试抓到了两处**,而且第一处是这一轮新引入的:

1. **`claimant` 重构把一条旧变异体的锚点弄丢了。** 我把
   `applyShiki(active === null ? stored : active)` 收敛成一个具名局部变量之后,
   变异体 `syntax-palette-never-applied` 的锚点文本不复存在,selftest 报
   **`INAPPLICABLE` 并计入失败** —— 这正是那条守卫存在的意义:一次重构悄悄
   断开一条变异,而它看起来还是绿的。锚点已更新。

2. **"把偏好写成 0" 那条变异体第一版是 `INCONCLUSIVE`(超时)。** 因为在
   `reconcile()` 里无条件 `prefs.set(...)` 会**无限重入**:写入 → 调度重新应用 →
   再次 reconcile → 再写。真实的错误实现会**加一个幂等守卫**(`&& prefs.isOn(...)`)
   所以会收敛,变异体现在也照着写 —— 而那条教训本身值得留着:**这个 bug 的第一形态
   不是"偏好被改坏",是"主题卡死"。**
