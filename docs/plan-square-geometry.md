# 方角几何 · 方案与实施记录

> **状态:已实施(2026-09-11)。** 实施过程中改掉了方案里的两处机制判断,记在 §3.1;
> 方案原文保留在上方,读者可以对照"当时以为"和"实际是"。开关仍是**默认关闭**的
> `soft`,新行为全在 `seal` 下——所以**除非你在设置里打开「极方圆角」,界面不会有任何变化**。

> **宗旨(用户 2026-09-11 定):尽量复刻参考设计。**
>
> 这条宗旨把项目的默认规则从"有理由地偏离"改成"有理由地复刻"——**偏离需要记录,复刻不需要**。
> 本文档只覆盖**几何**(圆角 / 细线 / 角形),因为它有一个必须先解决的技术前提。
> 其余待复刻项(薄染梯级、玻璃层、便笺面、焦点、纸纹三层、字距、链接细线…)记在
> §7,不在这份文档的实施范围内。

## 0. 这件事不是从零开始

`lib/client.js:1271-1295` **已经有一个「极方圆角」开关**:

```css
body[data-hana-theme][data-hana-shape='seal'] button,
body[data-hana-theme][data-hana-shape='seal'] input,
body[data-hana-theme][data-hana-shape='seal'] select,
body[data-hana-theme][data-hana-shape='seal'] textarea,
body[data-hana-theme][data-hana-shape='seal'] [role='button'],
body[data-hana-theme][data-hana-shape='seal'] [role='tab'] { border-radius: 2px; }

body[data-hana-theme][data-hana-shape='seal'] [data-composer-card] { border-radius: 6px; }
```

它默认关闭(`soft`),覆盖 `button`/`input`/`select`/`textarea`/`[role=button]`/`[role=tab]`,
并保留了参考唯一的例外——输入框留一点柔和(`6px`)。

而且它放弃全局重置的理由,**已经写在代码里**:

> 元素级 `border-radius:50%` 出现在 badges、rails、credential dots 上,所以
> `[class] { border-radius }` 重置会把它们压方,而"再放回去"意味着猜哈希类名。
> 只碰能命名的东西,就不需要恢复任何东西;这也避免了 `!important` ——
> `body[data-hana-theme][data-hana-shape] control` 是 `(0,3,1)`,已经压过
> CSS-Module 单类 `(0,1,0)`。
> **接受的取舍:这会把控件和输入框压方,而不是产品里每一个圆角矩形。**

**这份文档的任务就是回答它当时搁置的那个问题**:既然宗旨变成"尽量复刻",
这个"部分但安全"的范围**够不够**?如果不够,代价到底是多少?

## 1. 现状(全部实测,不是估计)

### 1.1 复制不是靠令牌,靠的是"选择元素"

参考的机制是**一个令牌改全局**:

```css
/* desktop/src/themes/new-warm-paper.css:62-69,覆盖 styles.css:33-44 的全局默认 */
[data-theme="new-warm-paper"] { --radius-sm: 2px; --radius-md: 3px; --radius-lg: 4px;
                                --radius-input: 2px; --radius-card: 3px;
                                --radius-chat-surface: 6px; --radius-chat-card: 4px;
                                --border-width: 0.5px; }
```

注释(`:3` / `:60`):**「极方圆角 + 0.5px hairline」** / **「controls are seals, 方」**,
并明说意图是**整个应用**,不止一个页面。

**DSH 没有对应物。实测(`tools/scan-geometry.mjs`,产物 `test/geometry-sites.json`):**

| 事实 | 数 |
|---|---|
| `border-radius` 声明总数 | **256**(35 个包) |
| 读取自定义属性的 | **0** ← 没有任何圆角令牌 |
| 不同取值 | 28 |
| 真正的圆/胶囊(`999px`/`50%`/`100px`) | 45 |
| 细线(`1px`) | 10 |
| 角向值(`12px 12px 0 0` 等) | 6 |
| `0` / `inherit` | 3 |
| **矩形刻度(要压方的真正目标)** | **192** |
| **只挂在构建哈希上的(按判据 5/16 不可达)** | **254 / 256** |

(192 + 45 + 10 + 6 + 3 = 256。逐条清单在 `test/geometry-sites.json`,按包/模块/语义名可查。)

所以:参考"改一个令牌就整个应用变方"的做法,**在 DSH 里没有对应机制**,
只能靠**选择元素**——而 254 个站点只挂在哈希类名上,判据 5/16 明令禁止钉哈希。

> **这就是那个前提。** 上一轮我说"方是部分可达";准确的说法是:
> **逐站点覆写只有 0.8% 可达,必须换机制。**

### 1.2 唯一一个全局几何杠杆:`--dsw-corner-shape`

DSH 的 `dsh-client-ui-theme` 里有一份 `corner-shape.css`:

```css
@supports (corner-shape: superellipse(1.5)) {
  :root { --dsw-corner-shape: superellipse(1.5) }
  *, :before, :after { corner-shape: var(--dsw-corner-shape) }
}
```

四个关键性质:

1. **它作用在 `*, :before, :after` 上**——也就是**整个应用,包括那 254 个够不着的站点**。
2. **它是一个 `:root` 上的普通自定义属性**,不是注册令牌(hana 的 allowlist 里没有它),
   所以 hana 用一条样式表规则就能改。
3. **`superellipse(1.5)` 比正圆更"软"。** 超椭圆指数 n:2 = 正圆,>2 越方,<2 越尖。
   也就是说 **DSH 的默认角比正圆还要圆钝**,而参考要的是**方**。
   提高指数(如 `superellipse(3)`)或直接 `round`,是朝着"方"的方向,
   **一行、全局、零附带损伤**。
4. DSH 有 **52 处**组件级 `corner-shape: round` 用来退出这个默认。
   **也就是说 DSH 自己已经标注了"这些是圆的"**——用 `corner-shape` 改全局时,
   这 52 处会自动保持圆形,**不需要 hana 维护任何"恢复名单"**。

**这是这份文档里最重要的一条**:参考用"一个令牌驱动全体"来做几何,
DSH 也有一处"一个令牌驱动全体"——只是驱动的是**角形**而不是**圆角大小**。

### 1.3 那 45 个圆/胶囊到底是什么

按站点语义(`locals`,从各 bundle 自己的 module map 恢复)分类,**合计 45**:

| 族 | 站点 | 典型语义名 | 压方之后 |
|---|---|---|---|
| **点 / 分隔** | **10** | `dot`×2, `credentialDot`, `requestDetailsDot`, `pending`×2, `status`×2, `separator`×2 | 6–8px 的盒子配 3px 圆角**看起来仍是圆点**,视觉基本无损失 |
| **圆形控件** | **21** | `iconButton`×3, `inspectButton`×4, `close`×2, `remove`, `clearButton`, `add`, `toBottom`, `search`, `control`, `trigger`… | **会变成圆角方块。但参考里这类控件本来就是 2px**(「controls are seals, 方」) |
| **徽章 / 胶囊** | **13** | `badge`×4, `chip`, `bar`, `rail`, `action`, `arrow`, `historyLoading`… | 参考的 chip 用 `--radius-sm: 2px`;`badge` 是唯一可能有争议的 |
| **图片 / 头像** | **1** | `thumb` | **只有这一族确实不该压方** |

**结论:全局压方的真正损失,只有图片缩略图一族(1 个站点)**,其余要么本来就该方,
要么尺寸小到看不出来。这比 `lib/client.js:1274` 当时的判断(暗示损失很大)要轻得多——
那条判断是在**没有清点**的情况下做的保守选择。

### 1.4 全局钳制在技术上是干净的

| 检查 | 结果 |
|---|---|
| DSH 在 `border-radius` 上用 `!important` 的地方 | **0** |
| DSH 用内联 `style={{borderRadius}}` 的地方 | **0** |
| 最高特异性 | 双类 `(0,2,0)`;hana 的 `(0,3,1)` 已压过;加 `!important` 则无条件胜出 |

所以"全局钳制"在 DSH 里**不会输给任何东西**。它当年被排除的原因是**语义**(怕破坏圆形),
不是**技术**。§1.3 表明语义上的损失被高估了。

## 3. 机制:三个杠杆,选两个

| | 杠杆 | 覆盖 | 附带损伤 | `!important` |
|---|---|---|---|---|
| **L1** | `--dsw-corner-shape` 调向"方" | **100%** | 无(DSH 的 52 处退出自动保留圆形) | 不需要 |
| **L2** | 全局 `border-radius` 钳制 | **100%** | 图片缩略图一族(≈2–4 站点) | **需要** |
| **L3** | 具名控件(现有实现) | 很小 | 无 | 不需要 |

### 3.1 实施时被推翻的两处判断

**(1)`!important` 用不了。** 方案里写"L2 需要 `!important`,而且技术上干净"
(DSH 在 `border-radius` 上用 `!important` 0 处、内联圆角 0 处)。
但 `test/check.js` 的判据 1 **明令禁止 `!important`**,要求"靠特异性取胜"。
于是改成把特异性算准——而这需要先测量 DSH 的天花板:

| DSH 圆角选择器的特异性 | 条数 |
|---|---|
| `(0,1,0)` 单类 | **239** |
| `(0,2,0)` | 19 |
| `(1,1)` | 5 |
| **`(3,0)`** | **3** ← 天花板 |

所以钳制必须到 `(0,3,1)`。这就是那些复合规则里那个"多余"的 `[class]` 的来历:
**它不是装饰,是一分特异性。** 而且控制层如果写成 `(0,2,2)`,会被自己的通用规则
`(0,3,1)` 打败、所有按钮都会拿到中号圆角——所以控制层也要带 `[class]`,落在 `(0,3,2)`。

**(2) `!important` 之外,方案还低估了一件事:`--dsw-corner-shape` 只在 `seal` 下设置。**
方案没有明说 L1 的作用域。实施时把它放进了 `seal` 的 body 规则里,而不是全局——
理由与 §4.1 一致:默认模式必须一个字节都不变。

**建议:L1 + L2 + L3 全上,但在同一个开关下**,理由:

- L1 单独不够:它改的是**角形**,不是**圆角大小**,而参考的立身之本是"小圆角"。
- L2 单独不够:它压不出参考那种"利落"的角,因为 DSH 默认角是**比正圆更软**的超椭圆——
  4px 的软角看起来仍然很圆。
- **L1 + L2 合起来才等于参考的效果**:小半径 **且** 正圆(甚至偏方)的角。
  这正好对应参考那句「极方圆角」——"极方"讲的是角形,"圆角"讲的是半径。

**顺序很重要:L1 先、L2 后**,并且两个都要能独立关闭——
这样万一 L2 的缩略图损失难以接受,可以只留 L1 回退。

## 4. 实施方案

### 4.1 开关

沿用现有开关,不改语义:

| 值 | 含义 |
|---|---|
| `soft`(**保持默认**) | 今天的行为,一个字节都不变 |
| `seal` | **新的完整方角**:L1 + L2 + L3 |

**为什么不改成默认 `seal`**:参考的 `new-warm-paper` 确实就是方的,但
(a) hana 的默认值此前是用户明确选定的;(b) 一次切换同时改变插件的**每一个**服务面,
万一出问题无法二分定位。**默认值是否翻转,是 §7 的第 1 个待定项**,不在本次实施内。

### 4.2 L1:`--dsw-corner-shape`

在 `seal` 下把角形调向方。取值需要**实测决定**,候选(按方到圆排序):

```
superellipse(4)  →  superellipse(3)  →  superellipse(2) = 正圆  →  round
```

`round` 是正圆弧,是**最保守**的一档(它把 DSH 的"比正圆更软"修回正圆,但没有变方);
`superellipse(3..4)` 才是真正的"方"。

**注意它会被那 52 处 `corner-shape: round` 局部覆盖**——这是**想要的**,
因为那些正是 DSH 标记为圆形的元素(头像、点、pill)。

### 4.3 L2:全局钳制 + 值映射

```css
body[data-hana-theme][data-hana-shape='seal'] *,
body[data-hana-theme][data-hana-shape='seal'] :before,
body[data-hana-theme][data-hana-shape='seal'] :after {
  border-radius: var(--hana-seal-radius, 3px) !important;
}
```

映射表(依据 §2,把 DSH 的 28 个取值折到参考刻度。**逐桶计数实测,合计 256**):

| DSH 现值 | 站点数 | 目标 | 依据 |
|---|---|---|---|
| `2px` `3px` | 12 | **不变** | 已在参考刻度内 |
| `4px` `5px` | 20 | **2px** | `--radius-sm` |
| `6px` `7px` | 36 | **3px** | `--radius-md` / `--radius-card` |
| `8px` `10px` `12px` `13px` | 72 | **3px** | 同上 |
| `14px` `16px` | 18 | **4px** | `--radius-lg` |
| `18px` `20px` `22px` `24px` `28px` `32px` | 34 | **6px** | 上限;只有输入框够格,见下 |
| `1px` | 10 | **不变** | 已是最细 |
| `0` `inherit` | 3 | **不变** | 本来就是方 |
| `999px` `50%` `100px` | 45 | **见 §1.3** | 按族决定,不是一刀切 |
| `12px 12px 0 0` 等角向值 | 6 | 逐角映射 | |

(12+20+36+72+18+34+10+3+45+6 = 256。)**注意 192 个矩形站点里,有 158 个的目标值落在
`2–4px` 区间**——也就是说参考的刻度不是"轻微收紧",而是把 DSH 的圆角**整体砍掉一半以上**。
这是本次改动里视觉冲击最大的一处,也是 §7 第 1 项(默认值是否翻转)要谨慎的原因。

**输入框例外要保留**(参考 `:67`):`[data-composer-card]` 与 textarea 走 6px,
和现有 L3 的写法一致。

> **`999px`/`50%` 怎么处理是本次唯一的真取舍。** 三个候选:
> **(a) 一起压 3px** —— 最贴参考(参考的 chip 就是 2px),损失缩略图;
> **(b) 保留** —— 安全,但产品里会留一批胶囊,和"方"的立意打架;
> **(c) 按族压、`thumb`/`img` 保留** —— 需要 `img` 和 `[data-role-icon]` 这类
> **可命名的结构选择器**兜住,覆盖率取决于这类钩子够不够。
> **建议 (c),失败则退到 (b)**,并把这个决定记进 §5。

### 4.4 L3:现有的具名规则保留,并且要自查描边宽度

现有 L3 是"能命名的就碰",在 L1+L2 之后它仍然有用:
它用**不带 `!important`** 的方式给出**正确**值,等于给钳制加了一层语义兜底。

同时要**审计 hana 自己的几何**,因为参考的 `--border-width: 0.5px` 是硬规则:

| 位置 | 现值 | 目标 |
|---|---|---|
| `lib/client.js:1066` 代码块描边 | `1px` | 0.5px |
| `lib/client.js:1180` 产物标记描边(`--hana-chip-edge`) | `1px` | 0.5px |
| `lib/client.js:1189` 末尾控件上边线 | `1px` | 0.5px |
| `lib/client.js:1058` 代码块圆角 | `3px` | 不变(已在刻度内) |
| `lib/client.js:1181` 产物标记圆角 | `4px` | 3px |
| `lib/client.js:1050` 印章圆角 | `2px` | 不变 |

**注意:hana 自己的几何已经是 2–4px 了。产品里的"圆"全部来自 DSH。**
这条值得写进文档,因为它说明这个主题的**自有意向早就是方的**,只是一直没敢推到 DSH 身上。

## 5. 必须记录的偏离(用户宗旨要求:偏离需记录)

即使 L1+L2 全上,下面这些**闭合不了**,要写成正式条目(不是注释):

1. **DSH 没有圆角令牌。** 参考的机制是"改 8 个令牌",这里只能是"全局 `!important` 钳制"。
   **形态不同,结果可以一致,但可维护性不同**:DSH 升级后 254 个哈希会换,
   我们的钳制**不受影响**(因为不钉哈希)——这反而是钳制相对逐站点覆写的**优势**,
   应该明说。
2. **`--dsw-corner-shape` 是未注册令牌。** 不在 token-allowlist 里,
   所以 DSH 升级可能改掉它。必须有一条**断言**在它消失时报错(§6)。
3. **嵌套减 2px 表达不了。** 参考的 `--radius-chat-card-inner` 是从外层派生的;
   CSS 无法读"当前值",所以钳制只能给**所有层同一个值**。
   后果:嵌套卡片的内外圆角不再同心。参考里这是刻意的同心设计,**这里会丢**。
   候选缓解:对已知的嵌套钩子(如 `[data-turn-process-member] [data-tool]`)单独给 2px。
4. **`thumb`/头像一族**按 §4.3 的决定处理,若选 (a) 则记录为已知损失。
5. **`--radius-chat-surface: 16px` 的原始身份丢了。** 参考把它降到 6px;
   DSH 的输入框是 `22px`(`Q7WfXG_card`)——我们给 6px,数值对得上,
   但**"输入框比其他元素略圆"这个相对关系**在钳制后不再来自令牌,而来自我们手写的例外。

## 6. 门(gates)

| 门 | 断言 | 变异 |
|---|---|---|
| `tools/scan-geometry.mjs --check` | 几何台账不过期;DSH 升级后站点变化会**主动报错**而不是静默漏掉 | 改一个值 → 台账过期 |
| 新增 `#36` | **`--dsw-corner-shape` 必须存在且被 hana 覆写**;解析失败即失败(防止 DSH 改掉这个未注册令牌后静默退化) | 删掉覆写 → 失败 |
| 新增 `#37` | `seal` 模式下,`[data-composer-card]` 的圆角**必须**大于其它控件(参考的例外条款) | 把例外也压到 3px → 失败 |
| 新增 check.js 判断 | `seal` 规则必须带 `!important`(否则压不过双类规则——这是**已验证**的失败模式) | 去掉 `!important` → 失败 |
| 新增 check.js 判断 | hana 自己的描边宽度必须是 `0.5px`(§4.4) | 改回 `1px` → 失败 |
| `test/verify/surface-check.mjs` | 真实引擎里读出 `seal` 模式下的计算圆角与 `corner-shape`,证明**生效**而不是"文件里有" | — |
| **`test/verify/seal-check.mjs`(已建)** | 把 DSH 在三个特异性档位上的**真实规则**取出来,放进真实浏览器,再设 `data-hana-shape='seal'`,读引擎算出来的圆角 | — |

**`seal-check` 是这份方案里唯一真正证明机制成立的东西**,而且它抓到了自己两次"通过得不对":

1. 第一版只断言 **CSS 文本**里有那几条规则。那证明不了引擎里生效——一个从未应用的钳制也能通过。
2. 第二版把真实规则搬进浏览器了,但 `(0,3,0)` 那条规则依赖 `data-side="details"`,
   而标记里没写这个属性 → 规则从未匹配 → **soft 模式读出 `0px` 而不是 DSH 的 `10px`**,
   而 seal 模式仍然读出 3px(来自通用钳制)。也就是说**最重要的那条特异性断言当时是空的**。
   第三版又把类名复制到了父元素上,而 `querySelector` 先命中父元素,测的根本不是规则指向的元素。

现在它报告的是引擎实测值:`seal` 下 `(0,1,0)/(0,2,0)/(0,3,0)` 三档全部 3px,
`soft` 下保持 DSH 的 `6px/6px/10px`。

**为什么第 2 条门最重要**:`--dsw-corner-shape` 是**未注册**令牌。
hana 对已注册令牌有 `tokens.test.js` 的两向断言;对这种未注册但**必须存在**的东西,
现在**没有任何东西**在看着它。这正是这个项目一贯要消灭的那类静默失败。

### 7.1 薄染四档:已实施(`tools/derive-wash.mjs`)

参考的阶梯**不是通用的**——对照色变体每一步都更重,这正是它的意义:

| 配色 | 源 | subtle | light | medium | strong |
|---|---|---|---|---|---|
| 纸本 | `new-warm-paper.css` | .03 | **.04** | .08 | .15 |
| 珊瑚 | `coral.css` | .03 | .05 | .08 | .15 |
| 青夜 | `midnight.css` | .03 | .05 | .08 | .15 |
| 斑斓 | `midnight-contrast.css` | **.04** | **.07** | **.11** | **.18** |

而色相是**主题自己的墨**:亮色配色取墨色(纸本 `rgb(42,38,34)`、珊瑚 `rgb(26,48,73)` —— 与参考逐位相同),暗色配色取**纯白**(参考自己就翻极性,`styles.css:58-59` 记着它当年因 box-shadow 踩过的坑)。

**实测 7 处漂移,全部修好**(`interactive-bg-hover` 等 5 个令牌 × 4 配色):

- **斑斓是反的**:`.04/.07` 比青夜的 `.05/.08` **更轻**——对照色配色成了四套里填充最弱的。
- 珊瑚 hover `.04` → `.05`。
- 纸本的 `sidebar-nav-item-hover` 是 `.05`,而它自己的 light 档是 `.04`——同一个界面里两个 hover 用不同 alpha。

**色相规则的第一次是错的**:第一版让暗色配色也取墨色,于是要把青夜六个**正确的纯白**薄染改成近白蓝 `#E1EAF0`,还把它写成"1/255 偏差"。是 `--check` 的漂移报告把这件事翻出来的——**交付的是对的,工具是错的**。

第四档 `strong` 在 DSH 里**没有消费者**(参考把它用在 Windows 滚动条 thumb 和分段控件滑块上;DSH 的滚动条是不透明令牌,也没有滑块令牌)。它**没有被硬塞一个消费者**:工具要求未被消费的档必须在 `UNCONSUMED` 里写明理由。

### 7.2 便笺面:已实施,但**结论与方案相反**

方案说"输入框是井,参考要亮片",并指向 `--jian-note-bg`。**映射错了。** 读了参考自己的 `input/InputArea.module.css`:它的输入框是 `background: var(--bg-card)`——**八条规则全是**。`--jian-note-bg` 妆点的是右侧的便笺编辑器,那个面 DSH 没有对应插槽。

而 `--dsw-specific-tip` 的三个消费者——**输入框、队列坞、目标条**——全是"落在纸上的一张卡"。
